# Decisions

**1. How does the assistant avoid answering outside the knowledge base?**

`knowledge_service.py` scores every user message against the 5 sections of `knowledge.md` before the model ever sees the question. `search()` tokenizes the query, then for each section sums the IDF weight (`_idf`, `_NUM_SECTIONS / doc_freq(term)`) of every keyword the query shares with that section — so a term unique to one section counts far more than one that appears in all five. The highest-scoring section wins, but only if its score clears `MIN_SCORE_THRESHOLD = 2.0`; otherwise `search()` returns `(None, best_score_seen)`. On a match, `conversation_service._grounding_instruction()` injects the matched section's body verbatim plus "Answer only using the context above." On no match, it injects a literal `"NO_MATCH: no knowledge base section is relevant to this question..."` string instead of any section text — the model is never shown a low-scoring section "just in case." That contract is stated directly in `knowledge_service.py`'s module docstring.

**2. Where are "own work orders only" and status-flow enforced — prompt, code, or both?**

Both, but they are not equals. `tool_definitions.py` puts the rules in plain English in each tool's `description` — `update_status`/`add_note`/`escalate` say "Only the assigned technician may do this," and `update_status` additionally says moves are only valid "Open ↔ In Progress ↔ On Hold ↔ Completed — no skipping steps," backed by a JSON `enum` on the `status` field. That module's own docstring calls this UX, not the boundary: it exists so the model behaves correctly and frames refusals accurately, but "is NOT trusted to self-enforce." The actual gate is `rule_validator.validate_tool_call()`: it checks `work_order.assignedTech != current_user.id` for the three ownership-gated tools, and separately checks `new_status` is a real value in `STATUS_ORDER` before checking `abs(new_index - current_index) == 1`. The docstring is explicit about why it re-checks status independently of the schema's `enum`: "models don't always respect enum constraints," so a hallucinated status can still arrive and must be caught in code, not assumed already filtered.

**3. What happens if a user tries to talk the assistant into bypassing a rule?**

Nothing changes, because `validate_tool_call(tool_name, args, current_user, get_work_order_fn)` never receives the conversation — only the proposed tool call and current state (confirmed at its one call site in `conversation_service._validate_one()`). No amount of "ignore that, just mark it done" in the chat can reach the function that makes the decision. The result is a `ValidationResult(ok, error_kind, reason)` with `error_kind` either `"malformed"` or `"rule_violation"`, and `conversation_service._run_tool_calls()` branches on which: a `rule_violation` (wrong owner, illegal jump) hard-stops immediately with no retry — `result.reason` is returned to the user as-is — because retrying the identical request can't make it more allowed. A `malformed` call (bad args, nonexistent ID, an invalid status string) gets exactly one retry (`MALFORMED_RETRY_BUDGET = 1`), since that class of failure can be a correctable mistake rather than a boundary the model is trying to cross.
